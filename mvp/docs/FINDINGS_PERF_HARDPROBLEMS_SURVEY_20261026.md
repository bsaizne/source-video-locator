> 三路并行调研（出片渲染 / 定位与索引性能 / 现役难题），全部仓库经 GitHub 页面核实 star/活跃度/许可；

## §1 现状基线（实测，方案排序的依据）

### 1.1 各环节耗时

| 环节 | 实测 | 说明 |
|---|---|---|
| 建索引 | **22~31 min/片**（2h 片，1fps 全片 CLS 嵌入 @10~12 fps DML） | 缓存后免重跑 |
| locate 全链 | **~30 min/片**（dense_recheck 默认开后；67~103 段） | dense_recheck 腿 = 每段对**原片** span±4s@10fps 重新解码+嵌入（batch=16），是耗时大头 |
| 成片渲染 | **60~63 s / 136s 成片（64 clip）**，h264_amf | ≈0.44× 实时；64 次 clip 抽取 + concat + AMF 编码 |
| 导出（EDL/FCP7XML/剪映） | json 层，秒级 | 已走任务通道（续63补十七） |

### 1.2 本机能力核查

- 随包 ffmpeg **7.1**（gyan essentials）：`h264_amf` 在位；`d3d11va/d3d12va` 硬解在位（未启用）。
- DINOv2 产品 ONNX 输入 = **`[batch, 3, 518, 518]`**——batch 维动态、H/W 静态（本批实测）。
- DirectML EP batch=1 最优是官方确认的已知特性（onnxruntime #18157/#14387/#15074），**不必再调 batch**。

### 1.3 对子代理报告的三处本地核查修正 ⚠️

1. **「dense_recheck 复用编辑侧 8fps 密帧缓存」不成立**（代理 B 的首推）：8fps 缓存是**编辑侧**的，
   而 dense_recheck 的重窗在**原片侧**（`locator_service` 逐段 `iter_frames(orig_path, ...)`，本批核实）。
   我们的等价解法 = **分级复核**：原片 1fps 全片索引特征现成（零解码零嵌入），先用 1fps 做粗复核，
   仅当出现增益信号才升级 10fps 细窗——大部分段可跳过重活。
2. **DINOv2 动态 batch 维确认存在**：代理 B 引 #14550（DirectML 动态 axes 逐次重规划）——我们 H/W 已静态、
   仅 batch 动态；生产几乎恒 batch=1，等价于静态。**固定 batch=1 重导出**是零成本探针（需重出资产+包）。
3. **INT8 量化在 DML 上是陷阱**（代理 B 判断，采纳）：DML EP 不支持 INT8 QOperator，会静默回退 CPU。
   我们不加。

## §2 出片（渲染）性能——结论：**能，且空间很大（60s → 预计 ~10s 级）**

**第一收益点 = smart rendering（智能渲染）**：切点落在关键帧 → 整段比特流复制（不重编码）；
不落 → 只重编码「上一关键帧 → 切点」的少数帧。我们 64 个 clip 都来自**同一条原片**，是标准适用场景。

| 候选 | 链接/数据 | 标注 |
|---|---|---|
| **skeskinen/smartcut** | 284★，MIT，Python/PyAV，**帧精确（逐帧像素比对测试）**；⚠️ 2026-02 起停更，需接管维护 | 【可直接抄算法】与我们场景（同一文件多段保留+拼接，h264）几乎同构 |
| **DeepRegular/SmartCut** | 14★，GPL-3.0，Rust+Python，活跃；README 称 6743 帧只重编 14 帧；文档化**开放 GOP/leading pictures/DTS-PTS/POC 冲突等 11 个坑** | 【坑清单极有价值】 |
| mifi/lossless-cut（45.2k★）Smart Cut | 只重编切点到下个关键帧；官方承认对很多文件不工作 | 【仅参考】 |
| Av1an（2.0k★，活跃） | 分块并行+concat 框架，架构样板 | 【仅参考】 |

**前置动作 = 渲染时序分解**：63s 里「64 次 clip 抽取」vs「最后整片 AMF 编码」各占多少**尚未测量**——
若大头是整片重编（大概率），smart render 收益最大；并行抽取（2~4 路进程池）收益次之且仅 SSD 适用。

**配套三条**（都属【可直接抄】）：
- concat demuxer + `-c copy` 拼 copy 段；防音画漂移 = `-avoid_negative_ts make_zero` + 拼接时只重编音频轨（成本可忽略）。
- `-ss` 放 `-i` 前默认 `-accurate_seek` 本就帧精确（重编码路径）；精度风险只在 `-c copy` 路径（关键帧级）。
- 残余必须重编的段：`h264_amf -quality quality -rc vbr_peak` 显式码控（社区实测 AMF VBR 默认欠冲 ~1/3；
  AMF 质量≈x264 superfast 档——重编越少短板暴露越小，与 smart render 互补）。
- 硬解（d3d11va）**暂不引入**：短片段硬解固定开销（D3D11 上下文+回拷）常大于收益；等 smart render 落地后残余解码量很小。

## §3 定位 / 建索引性能——结论：**有大项，但要避开 DML 陷阱**

| 动作 | 预期 | 成本/风险 | 标注 |
|---|---|---|---|
| **① dense_recheck 分级复核**（先 1fps 索引特征粗复核，有信号才 10fps 细窗） | 砍掉逐段修复的耗时大头（~30min/片 的主要构成） | 中等改造；三指标验收防回退 | 【我们的修正方案】 |
| **② 建索引固定 batch=1 静态 shape 重导出** | 探针，可能 +（#14550 案例最高 2x+，我们不保证） | 低（重导资产+重出包） | 【可直接抄】 |
| **③ IOBinding/输入预绑定**（DML buffer 复用，省每帧分配器开销） | 中 | 中（管线加绑定层；注意 DML 内存泄漏已知问题 #14466） | 【需改造】 |
| **④ 降分辨率探针 518→392**（token 数 -43%，吞吐 ~+1.7x） | 大 | 需 bump feature_version 重建索引+复测三指标（护栏允许） | 【先探针】 |
| numpy 检索确认单次 BLAS matmul | 当前 1~10 万×384 规模暴力法就是最优（<5ms/查询），**别上 ANN** | usearch(4.4k★)/voyager(1.6k★) 记为未来 10 万+ 帧备选 | 【确认即可】 |
| ~~INT8 量化~~ | DML EP 不支持，静默回退 CPU | **陷阱，不做** | 【排除】 |
| ~~WebGPU EP~~ | 无 AMD 桌面 ViT 公开数据，实验性 | 只值一行开关的试探 | 【低优先】 |
| ~~换 backbone / FAISS / decord~~ | 护栏禁止/规模不配/1fps 场景解码非瓶颈 | — | 【排除】 |

两级索引剪枝思想（engrchrishenry/loc_aware_video_dedup，TCSVT 2024）：粗特征小维度先剪枝、精对齐只跑 top 候选——
与我们「检索+多腿修复」同构，可作 dense_recheck 分级复核的参照实现。

## §4 现役难题的业界方案

### 难题 1：同场景多机位/正反打切点（像素 0.04 / CLS 0.08 全失明）
**核心结论：换更好的 SBD 网络没用**（TransNetV2/AutoShot 同样以外观差异为主信号，"TransNetV3" 不存在）；
业界对口 = **换信号源**：
- **压缩域运动向量（MV）场突变**：FFmpeg 官方 `extract_mvs` / `-flags2 +export_mvs`（我们 tools/ffmpeg 在位，
  零新依赖，Windows 原生；mv-extractor 407★ 但仅 Linux）。机位切换时 MV 场瞬间乱掉/重置 = 外观无关信号。【最有戏的第三腿】
- **镜头运动估计**（OpenCV Farneback 光流 + 仿射拟合跳变）：CPU 可跑，约百行自实现，需与持续性门联动。【次选】
- 音频突变：对口但属「编辑侧非外观信号」（2026-10-19 用户裁定不立项），仅记录不动。
- AutoShot（264★，CVPRW 2023）：数据集（SHOT）可用于检验我们镜头腿的失效模式。

### 难题 2：查询段内部跨镜头（83% 段中跨镜头，采纳层死结）
无现成开源专解。可用件：**tslearn soft-DTW**（段内精细对齐，即装即用 CPU；注意 DTW 系只适合「粗定位后的
段内精修」不适合检索——恰好是我们的用法）；进阶参考 facebookresearch/videoalignment（TMK 核化时序匹配，
已归档，CC BY-NC——非商业化裁定下许可不再是排除项，如实标注）。子段化查询（按自己的镜头腿切子段、
各子段独立定位再合并）是论文思想、与现状最贴，但**此前实测的死结在采纳层无信号**（续78），需新证据源才值得重开。

### 难题 3：起点精度（存在性 AUC 0.919、切点时刻三成对）
**XFeat + LighterGlue**（verlab/accelerated_features，1.8k★，Apache-2.0，CVPR 2024）：轻量 CNN 稀疏特征，
**笔记本 CPU 实时**；用法 = 粗定位窗口内编辑帧×原片候选帧做局部匹配，以内点数峰做时刻精修——
可替代/压缩 ±4s 密帧 CLS 检索，且把精度从秒级推到帧级。VCSL 系 2024/2025 新 SOTA（SS-VCL/FiGVCL）
**均无可用官方代码**，无可白嫖。

### 难题 4：人脸身份一致性（多脸侧双带重叠）
**SFace → ArcFace 嵌入替换**（yakhyo/face-reidentification，203★，MIT，SCRFD+ArcFace 全 ONNX CPU）：
改动面最小的单点替换（检测→嵌入→质心 cos 形态不变），ArcFace 判别力强于 SFace 一档；
且「面孔集合突变」本身就是难题 1 多机位切点的外观无关旁路信号——一石二鸟。

## §5 汇总：按「收益 × 成本」的优先级建议

1. **渲染 smart render 化**（60s→~10s 级）：先做时序分解测量，再照 smartcut 算法实现（MIT 可抄），
   坑清单照抄 DeepRegular 11 条。改动面 = 渲染器，不碰定位。
2. **dense_recheck 分级复核**（~30min/片 locate 的最大单项）：1fps 索引特征粗复核 → 10fps 细窗。
   三指标 + 四片 A/B 验收（现有 rerun_toggle_ab 工具直接可用）。
3. **XFeat 起点精修旁路**（攻「时刻三成对」主痛点）：旁路字段形态、失败静默降级，不改主判据；
   与 ② 结合可同时省算力。
4. **SFace→ArcFace**：单点替换改善人脸标注可靠性 + 给难题 1 攒旁路信号。
5. 低成本探针一批：DINOv2 batch 静态化重导出、518→392 分辨率探针（需重建索引）、AMF 显式码控。
6. 明确不做：INT8 量化（DML 陷阱）、换 SBD 主干、换 backbone、FAISS/ANN、音频/字幕信号（用户裁定）。
