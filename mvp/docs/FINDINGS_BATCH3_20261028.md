## 2. B3-3 smart render = 第二次判负（永久关闭）

### 2.1 复现与根因（10-27 那次没定位到这一层）

- 现象：test3 真片容器 4513 帧、**严格解码只有 1975 帧**。件级排查：每个 part 单独解码都完整
  （head 93/93、copy 194/194、tail 25/25），但三段 concat 后只出 93 帧 ⇒ 断点在**段内拼接**。
- 根因：重编件与 copy 件的**码流参数不一致**——源片 `has_b_frames=2`、AMF 默认编出 `bf=0`。
  只对齐 profile/level（Main↔High）**无效**；`setts`/`genpts`/`copyts`/`video_track_timescale`
  四种 muxer 手段**全部无效**；**补 `-bf <源 has_b_frames>` 后 312/312 全解码**。
- 已在生产路径落地：`segment_command(..., b_frames=)`，仅 smart 路径传参（串行重编行为逐字不变），
  单测锁住「smart 传源 B 帧数 / 串行不带 `-bf`」。全片复验：容器 4513 / 严格 4513 / 预期 4513。

### 2.2 修好之后的真读数（这才是判负依据）

| 臂 | 墙钟 | 严格解码 | copy 帧 | CFR |
|---|---|---|---|---|
| off（逐段重编） | **36.54s** | 4513/4513 | 0 | 0.0417 恒定 ✓ |
| on（smart） | **72.01s** | 4513/4513 | **279（6.18%）** | PTS 间隔 −0.292~8.42 ✗ |

- **copy 占比只有 6.18%**：test3 的 101 个片段多为 1~2s 短段，而源片关键帧间隔约 4s
  ⇒ 绝大多数片段根本没有完整 GOP 可复制。
- **墙钟反慢一倍**：每个片段被拆成 3 件（重编头/复制中/重编尾）+ 两级 concat，
  并行度被拆碎；而 off 臂 101 段是 6 线程全并行。
- **输出破坏 CFR**：PTS 间隔 −0.292~8.42（DTS 单调但 PTS 不单调），违反成片恒定帧距语义。

⇒ 结论：**smart render 在本项目素材形态下结构性不成立**（H.264 源也很少，四片只有 test3 一片）。
维持 `smart_render_enabled=False`，**不再重试**；保留本次的 `b_frames` 修正（它让存档路径成为正确实现，
但默认不启用）。

## 3. 一个仪表教训（自留）

首版件级探针把 `nb_read_frames` 漏在 `-show_entries` 之外 ⇒ **连重编件都报严格解码 0**，

`-show_entries`，且先用一个已知良好的件做自证。
