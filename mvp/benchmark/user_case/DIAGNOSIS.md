## 判定：是算法问题，不是 bug

**不是代码 bug**（已排除）：
- 时间基错位：原片 `2.mkv` 与编辑片 `1.mp4` 的 `format.start_time` / `v:0.start_time` 均为 0.000000；索引时间轴（帧计数 t=i/fps，0~7666s）与预览/抽取 seek（容器真实时间）一致 ✓
- 索引错位 / device 回退 / embed 报错 / validate INVALID：未出现；device=directml(amd)；索引复用 `2__4c6d4ab2.idx` ✓
- 预览抽取用的就是 `Result.original` 区间，无二次换算 ✓
- 复现输出与 App 日志逐项一致（同 12 段 / HIGH5 / MED1 / LOW6 / 485 候选）→ 无回归、无环境差异 ✓

**是算法限制，两个已知失败签名叠加**（研究期已文档化）：
1. **蒙太奇定位丢失子镜头（主因，命中全部 12 段）**：`detect_shots` 产出的是**长蒙太奇单元**（如 seg2=8–36.5s 一段含站台+暗室+铁丝网多个不同镜头；seg6/seg7 也各 22s+），而冻结 `finloc longest_run` 对每个段**只返回一条最长连续原片区**，只覆盖蒙太奇里的**一个子镜头**，其余子镜头全部丢失 → 「编辑片里有的内容，解析出来的原片里没有」。这正是研究 Phase 17A/18/19 已证伪过「per-query argmax / voting / cut-aware 都净收益为负、不可采纳」的同一限制；研究贯穿主因「**相似外观（暗色+军人/人物+纹理）掩盖语义身份**」。
2. **相似外观误配（次因，最危险）**：seg11 把 TikTok 水印/搜索框（黑底白 logo）误配到电影片尾演职员表（黑底白 logo）——外观相似但语义完全不同，却 **HIGH 0.904**。seg3/seg4 也是蒙太奇部分命中但 HIGH。

**产品最危险点 =「自信地答错」**：置信度是**未标定占位**（CONFIDENCE_DESIGN §6 / TODO 第 11 项），它**没有**对「蒙太奇部分命中 / 内容异构 / 超宽窗 / logotype 卡片相似」做降档，于是 seg3/seg4/seg11 这类错/部分命中拿到 HIGH。鉴证：seg11 高相似、无 hard_flag（窗 30s<60s、无 low margin、无 montage flag）→ 直接 HIGH。

## 可行处置（合规：不改相似度/检索/排序/定位/置信语义）

1. **置信度标定（TODO 第 11 项，最高价值、最合规）**：用这份真实数据校准 `ConfidenceConfig` 权重/阈值，让「蒙太奇部分命中 / content异构（logotype 卡片、暗色人物）/ 超宽窗」落到 LOW 而非 HIGH 错答。把「自信答错」变成「诚实不确定」，这是产品安全第一步，也**不改任何冻结算法语义**。
2. **UI 蒙太奇明示**：montage 段 / 部分命中段，明确标注「可能是转场/多镜头拼接，当前只定位到其中一段」，并展示 `alternatives`，引导用户不当精确匹配。
3. **真正提升蒙太奇定位能力（可选，需你拍板）**：把「单片段返回一条原片区」升级为「一个蒙太奇段返回多个子镜头原片区」。这是**能力升级 = 新研究阶段**（research guardrail 允许：现在有真实用户数据证明该失败显著影响产品价值）。先前 17A/18/19 方向被证伪，需**新的方向**（如场景身份/时序一致性第二信号、或多段并集输出）。
