## 0. 结论（三条）

1. **收益错配（硬结论）**：索引密度 ÷2（1.0fps → 0.5fps）的收益**全部落在一次性成本**上——
   本测试集四片真实索引合计 **31,117 帧 / 38.1 分钟（13.6 fps 折算口径）**，÷2 省 **19.1 分钟**
   与 **26.6 MB**（53.2→26.6 MB）；**每次定位（现役默认 45~60 分钟/片，test1 实测 46.2 分钟）
   一分钱不省**——宽扫（ISC ±90s，占定位主成本的大头）与抓帧**不经索引**（源码事实：
   `isc_refine.apply_isc_refine` 用 `_grab_many(source_path, coarse_ts)` 按任意时刻抓帧，
   与 `lib_times` 网格无关）。
2. **精度侧不是阻碍（本批实测）**：把现役默认批（严格 136 / 导出 131 / 场景 138 / 负例 4·9）
   的**原片侧 span 端点吸附到 2s 网格**（= 0.5fps 提案网格的量化上界，偏差 ≤1s）后重算 =
   **严格 137 / 导出 131 / 场景 138 / 负例 4·9**（严格 +1，唯一翻转 t1r12a part→HIT）。
   即「网格粗化 ±1s」在本口径下**零代价**。真正的风险形态是**系统性缩短**（两端各 −1s =
   严格 −18 / 导出 −48），但它不是「索引变粗」的机制（真实链路端点由 patch/ISC 局部细化给出，
   实测落在 0.25s 步长上，非索引网格）。
3. **裁决建议 = 不立项（或降级为「仅新装机可选项」），并把同一条「两级采样」思路搬到真正花钱的
   地方**（ISC 宽扫的自身两级参数：粗步长 2.0s → 4.0s）。密度轴此前的三次关闭（研究侧 8fps、
   生产侧 2fps、读图复核）都发生在**加密**方向且结论一致为「饱和」；本批补上了**抽稀**方向的
   敏感度上界，结论同样是「不构成精度阻碍」，于是本杠杆的价值完全由「一次性 vs 每次」的成本
   结构决定 ⇒ 收益/风险比不划算。

## 2. 成本账：收益落在「一次性」，痛点在「每次」（本批核心）

### 2.1 真实索引元数据（四片，应用数据目录 `data/index/*.idx/index.json`）

| 片 | 帧数 | 源片时长 | 索引体积 | 建索引折算 @13.6fps | ÷2 后省 |
|---|---|---|---|---|---|
| 2mkv | 7,668 | 7,667.5 s | 13.2 MB | 563.8 s | 281.9 s |
| test1 | 8,221 | 8,229.3 s | 14.0 MB | 604.5 s | 302.2 s |
| test2 | 5,051 | 5,050.6 s | 8.6 MB | 371.4 s | 185.7 s |
| test3 | 10,177 | 10,177.1 s | 17.4 MB | 748.3 s | 374.1 s |
| **合计** | **31,117** | **31,124 s (8.65 h)** | **53.2 MB** | **2,288 s (38.1 min)** | **19.1 min / 26.6 MB** |

- 四片 `index.json` 一致：`sampling_fps = 1.0`、`feature_version = handwritten_vits14_cls_384d@1_l2+scn1+evt1`、
  `backend = directml`、`resize 518x518`、`preprocess_sha 89b313a16bc8553f`。
- 吞吐口径 = 续17 实测（H2 DirectML 建索引 10/60/128 min → 44.6 / 260.3 / 562.7 s = 13.5~13.8 fps）；
  本表按 13.6 fps 折算，**非本批实测**（不重跑索引，见 §6 边界）。

### 2.2 每次定位的成本结构（为什么索引密度碰不到它）

| 阶段 | 是否随索引帧数缩放 | 证据 |
|---|---|---|
| 建索引（一次性） | **线性**（帧数 ÷ 13.6 s） | §2.1 |
| 检索 matmul / CLS 聚簇 / finloc / 覆盖 | 线性但绝对值极小（31k×384 级矩阵） | 索引驱动；量级 < 秒级 |
| **ISC 宽扫（±90s，定位主成本）** | **否** | `isc_refine.apply_isc_refine`：`_grab_many(source_path, coarse_ts)` 按**任意秒**抓帧 + ISC 现算，粗扫点由 `scan_radius_s`/`WIDE_COARSE_STEP` 决定，与 `lib_times` 无关 |
| 抓帧（shot_split / patch_refine / 窗解码） | **否** | 续34 归因：grab 占两旋钮段 77.6% wall；全部按任意时刻抓帧 |
| 编辑侧嵌入 / 双特征 | 否（编辑侧缓存） | 续34 `embed.dual 10.8%` |

⇒ **索引密度 ÷2 对「每次定位 45~60 分钟」的影响上界 = 索引驱动阶段占比**；该占比落在续34
实测的「pre-knob 段 P = 387.5 s / 1052.4 s」之内，而 P 的大头是编辑侧嵌入，不是索引扫描。
**一句话**：÷2 让「第一次用一部 2 小时片」从 ~9.4 分钟建索引降到 ~4.7 分钟，之后每次定位
（45~60 分钟）不变。

### 2.3 为什么这条与用户痛点错配

- 一次性成本 = 每部源片 9.4~12.5 分钟（2h 档），÷2 省 4.7 分钟，**且只省一次**（之后复用索引）。
- 每次定位 = 45~60 分钟/片（现役默认：radius=90 + 窗解码，test1 实测 46.2 分钟）。
  用户一天跑 5 条成片 = 4 小时级；建索引的 4.7 分钟在其中占比 <2%。
- ÷2 的**附带代价**：`feature_version` bump ⇒ 存量索引全部失效、用户库需重建一次
  （重建本身按新成本计算，故不是净亏，但会触发一次全库重跑与 UI 上的「索引过期」告警面）。

## 3. 精度敏感度实测（本批新增探针）

脚本：`mvp/scripts/probe_index_fps_sensitivity.py`（零 runtime、零 GPU）
输入：现役默认批 `work/isc_refine_arms/v2_*`（= 续45 v2 宽扫臂；与续46 补「翻默认」后配置一致）
评估器：`measure_shot_recall.evaluate`（与三指标同一口径，未改写）
扰动：只作用**原片侧 span**（main + `original_segments`），编辑侧不动。

| 扰动模式 | 含义（= 提案网格粗化的哪一类误差） | 严格 | 导出实得 | 场景 | 负例 | 翻转行 |
|---|---|---|---|---|---|---|
| base | 现役默认批 | **136/139** | **131** | **138** | 4/9 | — |
| **grid2** | 端点吸附最近 2s 网格（偏差 ≤1s） | **137 (+1)** | **131 (0)** | **138 (0)** | 4/9 (0) | 1（t1r12a part→HIT，**增益**） |
| shrink1 | 两端各缩 1s（最坏覆盖损失上界） | 118 (−18) | 83 (−48) | 128 (−10) | 4/9 (0) | 22 |
| shift_minus1 | 整体提前 1s | 132 (−4) | 124 (−7) | 138 (0) | 4/9 (0) | 4（p16/p39/t2r06a/t3r32，全 HIT→part） |
| shift_plus1 | 整体推后 1s | 135 (−1) | 130 (−1) | 138 (0) | 4/9 (0) | 5（含 t1r08c/t1r12a part→HIT 两条增益） |

**判读**：
- **量化（grid2）零代价**——现役读数对「±1s 端点吸附」完全不敏感，唯一翻转还是增益。
  说明最终 span 的判据余量普遍 ≥1s（判据含 `within ±2s` 与 `cov ≥ 0.4` 双通道）。
- **平移 ∓1s 只影响 4~5 行**（−1 ~ −4 严格），且方向不对称（晚移几乎无损）。
- **收缩 1s/端是唯一的大损失形态（−18/−48）**，但它是「span 变短」而非「网格变粗」；
  0.5fps 索引若仍走 patch/ISC 局部细化（现役默认开），端点不会各自向内缩 1s。
  ⇒ 该行作为**上界**登记，不作为 ④ 的预期损失。

## 5. 裁决建议与替代杠杆

### 5.1 建议（待用户拍板）

- **(a) 不立项**（推荐）：收益落点在一次性建索引时间（每片省 4~6 分钟、一次性）与索引体积
  （53.2→26.6 MB），与「每次定位 45~60 分钟」的痛点错配；且需要 `feature_version` bump
  + 四片全回归（≈3~4 h 机时）+ 存量索引失效一次。**用 3 小时机时买「每片一次性省 5 分钟」
  不划算**，属于典型「结构账一页纸即可判负」。
- **(b) 降级立项**：只作为**新装机默认值调整**（注意：`sampling_fps` 进 `feature_version`，
  不存在「不 bump 语义版本还能改密度」的做法），或作为「长片库」场景的可选档（10 h 级源片才显性）。
- **(c) 若仍要实跑**：执行方案已备——`SVL_DATA_DIR` 指向隔离根（避免覆盖生产索引）→
  `FeatureStore(sampling_fps=0.5)` 重建四片索引（≈19 分钟）→ 现役默认批同配置四片全跑（≈3 h）
  → 与 `work/isc_refine_arms/v2_*` 逐 ID 比对三指标 + 翻转读图。**成本 = 3.5 h 机时；
  预期结论已由本结构账给出（精度近零变化、定位耗时近零变化）**。

### 5.2 替代杠杆（同一「两级采样」思想，搬到真正花钱的地方）

现役 ISC 宽扫**已经是两级**（粗 2.0s + top-3 峰 ±2.0s @1s 细化），其成本 = 91 粗点 + 15 细点
≈ 106 embeds/段（radius=90；续45 实测 +88 分钟/四片）。**粗步长 2.0s → 4.0s** 可把粗点 91→46
（−42% 宽扫 embeds），代价 = 粗峰值分辨率减半（top-3 细化半径不变，仍 ±2.0s）。

- **结构账能不能零 GPU 做？** 不能——需要**每个歧义段的 ISC 粗曲线**，runtime 不落盘、
  既有 `work/orthogonal_backbone/` 只存了 PNG。⇒ 需要的是一次**小样本曲线探针**：
  取 20~30 段（MISS6 + 口袋 + 若干 CONTROL），在 ±90s 上以 **1.0s 步长**落盘 ISC 曲线
  （每段 ~180 embeds，30 段 ≈ 5,400 embeds ≈ 5~10 分钟 GPU），离线比较
  「粗步长 2s + top-3 细化」 vs 「粗步长 4s + top-3 细化」的**峰值保持率/落点差**。
- 门槛建议：峰值保持 ≥ 95% 且落点差中位数 ≤ 1.0s ⇒ 值得进四片回归；否则判负。
- 这条与本批结论同源：**优化的收益必须落在「每次」而不是「一次」**。
